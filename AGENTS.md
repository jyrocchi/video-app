# Guía para agentes: JyroCam

- **Proyecto vigente:** `CamStreamApp/` (Android, Kotlin/CameraX/MediaCodec) + `CamStreamDesktop/` (Electron/Node, FFmpeg y cámara virtual DirectShow). No confundirlos con `server.js`, `phone.html` o `viewer.html` de la raíz: son el prototipo anterior.
- **Inicio y pruebas de PC:** trabajar desde `CamStreamDesktop/`: `npm ci`, `npm test`, `npm start`. `npm run pack` genera `dist/win-unpacked/JyroCam.exe`; `npm run build` genera `dist/JyroCam-Portable-1.0.2.exe`. Solo una instancia puede usar el puerto 8080. `virtual-cam/build.bat` recompila `bin/JyroCamVirtualCam.dll` antes de empaquetar.
- **Android:** trabajar desde `CamStreamApp/`: `.\gradlew.bat :app:assembleDebug` (Gradle 8.13/JDK 17, compileSdk 36, AGP 8.13.2, Kotlin 2.2.21, CameraX 1.6.2). El APK debug queda en `app/build/outputs/apk/debug/app-debug.apk`, con ID `com.anomaly.camstream.debug`; minSdk 24 y targetSdk 34.
- **Configuración validada:** perfil fijo 1280×720 a 30 FPS, Rotar oculto/deshabilitado, referencia de orientación fija. Codificador Qualcomm del Motorola edge 30 fusion en CBR 6000 kbps, transporte H.264 limitado a 8000 kbps. Visor, NDI y cámara virtual DirectShow entregan 1280×720; reconstruir/actualizar la DLL al cambiar este formato. Mediciones y comandos en `CamStreamDesktop/PERFORMANCE.md`.
- **Transporte:** Android envía NAL H.264 con longitud prefijada mediante `POST /stream-h264` persistente; la PC expone `/status` y `/frame.jpg`. `POST /upload-h264` queda como compatibilidad con escritorios anteriores. Mantener el orden de NAL y el control de presión de FFmpeg.
- **Distribución:** JyroCam 1.0.2 corresponde a `compatibilidad-android-resolucion-fija`, título «Compatibilidad android + resolución fija». Versiones anteriores conservadas en Releases. Se mantienen applicationId Android, appId Electron, CLSID y nombre de memoria compartida. `dist/`, `app/build/`, `.gradle/` y `node_modules/` son artefactos ignorados; los descargables se adjuntan al release, no se usan como fuente de verdad. No borrar la única compilación disponible antes de crear su reemplazo.
- **Diagnóstico:** el registro en Android muestra `sensor`, `capt`, `yuv`, `up q`, `wait`, `dec`, `pipeQ`, `JPEG` y `render`. Colas actuales vacías no demuestran latencia extremo a extremo nula. El ADR del MCP `video-app` conserva las mediciones históricas; actualizarlo tras mediciones reales.
- Mantener la capacidad de construir y probar **ambos extremos** cuando se cambie el protocolo. No reducir resolución/calidad para tratar latencia sin pedirlo explícitamente.
- **Espejo/Wi-Fi/Android:** usar `YuvFramePacker` para el camino 720p fijo; no volver a JNI por píxel. Wi-Fi con/sin espejo ~30 FPS, locks ligados al servicio. `startForeground` tipado solo desde API 29. Matriz funcional Android 7–17 en `CamStreamApp/COMPATIBILITY.md`: Android 17 requiere `CAMSTREAM_EMULATOR_DISABLE_LUMA=1` en el AVD (ajuste gráfico), no en la app/dispositivo. El harness usa AVD propios/receptor 18081. MediaCodec libera buffers antes de callbacks y serializa acceso/parada; no reintroducir la carrera de release. Una consulta de capacidades fallida no implica escritorio antiguo. El hilo DirectShow usa `timeBeginPeriod(1)` solo mientras captura y lo equilibra con `timeEndPeriod` para no depender de `Sleep(1)` de ~15,6 ms.

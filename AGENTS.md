# Guía para agentes: JyroCam

- **Proyecto vigente:** `CamStreamApp/` (Android, Kotlin/CameraX/MediaCodec) + `CamStreamDesktop/` (Electron/Node, FFmpeg y cámara virtual DirectShow). No confundirlos con `server.js`, `phone.html` o `viewer.html` de la raíz: son el prototipo anterior.
- **Inicio y pruebas de PC:** trabajar desde `CamStreamDesktop/`: `npm ci`, `npm test`, `npm start`. `npm run pack` genera `dist/win-unpacked/JyroCam.exe`; `npm run build` genera `dist/JyroCam-Portable-1.0.3.exe`. Solo una instancia puede usar el puerto 8080. `virtual-cam/build.bat` recompila `bin/JyroCamVirtualCam.dll` antes de empaquetar.
- **Android:** trabajar desde `CamStreamApp/`: `.\gradlew.bat :app:assembleDebug` (Gradle 8.13/JDK 17, compileSdk 36, AGP 8.13.2, Kotlin 2.2.21, CameraX 1.6.2). El APK debug queda en `app/build/outputs/apk/debug/app-debug.apk`, con ID `com.anomaly.camstream.debug`; minSdk 24 y targetSdk 34.
- **Configuración validada:** perfiles seleccionables 720p30 / 720p60 / 1080p30, definidos en `StreamProfile.kt` y `stream-profiles.js`. H.264 6000/10000/12000 kbps, pacing 8000/14000/16000 kbps; Baseline niveles 3.1/3.2/4.0. Camera2 filtra tamaño YUV, duración mínima y rango AE; MediaCodec filtra tamaño/FPS/bitrate/color y prioriza hardware. Motorola trasero admite los tres, frontal no 60 FPS. Rotar sigue oculto. USB y Wi-Fi medidos, detalles en `CamStreamDesktop/PERFORMANCE.md`.
- **Transporte:** Android envía NAL H.264 con longitud prefijada mediante `POST /stream-h264`, cabecera `X-JyroCam-Profile` (`720p30`, `720p60`, `1080p30`). Ausente = 720p30; desconocida = 400. `/status.video.profiles` anuncia soporte; perfiles nuevos requieren PC actualizada. Reiniciar FFmpeg entre sesiones; mantener orden, contrapresión y descartar callbacks de procesos antiguos. `/upload-h264` conserva compatibilidad 720p30.
- **Distribución:** JyroCam 1.0.3 «Perfiles HD y Full HD» incorpora los tres perfiles en `compatibilidad-android-resolucion-fija`; Android versionCode 4 / versionName 1.0.3-debug, ID `com.anomaly.camstream.debug`. Notas y hashes en `RELEASE_NOTES_1.0.3.md` / `checksums-1.0.3.sha256`. Versiones anteriores conservadas en Releases. Se mantienen applicationId Android, appId Electron, CLSID y nombre de memoria compartida. `dist/`, `app/build/`, `.gradle/` y `node_modules/` son artefactos ignorados; los descargables se adjuntan al release, no se usan como fuente de verdad. No borrar la única compilación disponible antes de crear su reemplazo.
- **Diagnóstico:** el registro en Android muestra `sensor`, `capt`, `yuv`, `up q`, `wait`, `dec`, `pipeQ`, `JPEG` y `render`. Colas actuales vacías no demuestran latencia extremo a extremo nula. El ADR del MCP `video-app` conserva las mediciones históricas; actualizarlo tras mediciones reales.
- Mantener la capacidad de construir y probar **ambos extremos** cuando se cambie el protocolo. No reducir resolución/calidad para tratar latencia sin pedirlo explícitamente.
- **Espejo/Wi-Fi/Android:** usar `YuvFramePacker` con tamaño nativo; no volver a JNI por píxel. Locks ligados al servicio, `startForeground` tipado desde API 29. Matriz Android 7–17: cuatro pruebas por AVD en `CamStreamApp/COMPATIBILITY.md`; no confundir codec sintético con FPS de cámara real. Android 17 requiere `CAMSTREAM_EMULATOR_DISABLE_LUMA=1` solo en AVD. Harness aislado en 18081. MediaCodec libera buffers antes de callbacks y serializa acceso/parada. Una consulta de capacidades fallida no implica escritorio antiguo.
- **DirectShow:** tres formatos RGB24; memoria compartida conserva nombre y cabecera de 32 bytes, capacidad 1920×1080×3 + DWORD FPS al final. Reconstruir/actualizar DLL y reabrir consumidores tras cambiar resolución. Copiar tamaño validado desde snapshot local para evitar carreras al cambiar perfil. Cadencia guiada por cuadros nuevos, `timeBeginPeriod(1)` equilibrado; limitar a 30 solo si el consumidor lo pide a un productor de 60. Test FFmpeg necesita `rtbufsize` para cuatro cuadros (el predeterminado apenas admite uno 720p y descarta cuadros).
